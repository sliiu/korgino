# 性能和鲁棒性只修有把握的问题

## 结论

这一轮看了全部代码，只改能确认会出错或明显卡顿、改动又小的地方，不做大重构。

改了：

- `Background.run` 的调用方被取消时，后台那份工作一起取消。以前取消只是丢掉结果，网络请求照跑完、照扣额度。
- 划词浮层被用户关掉（Esc、点外面、关最后一个标签）时，取消还在跑的翻译，免得旧结果落进下一个浮层或 OCR 草稿。浮层自己换内容时不取消。
- 实时字幕的逐句翻译按“句子 + 翻译服务”记任务。以前只按句子记，补译另一家会把前一家的请求取消掉，那一家永远停在“翻译中…”。停止听写时，已经发出去的翻译让它译完，句子还在屏幕上。
- 麦克风的音频缓冲先复制再交给识别队列。系统在回调返回后可能复用那块内存。
- Whisper 请求超过 22 秒被放弃时，同时清掉“识别中”状态。
- 正在申请权限时再点开始，不再起第二路采集。
- 音量表在音频线程就先限到每秒约 15 次，再回主线程。
- 网络会话不再每个请求读一次钥匙串里的代理密码；代理设置改动停顿 0.4 秒后才重建会话，打字时不打断进行中的请求。
- 历史记录的“读、插入、写回”加锁，几路同时写入不再丢条目；文件不再缩进排版。
- 收藏的“是否已收藏”在内存里查，不在每次界面刷新时读盘解码。
- 文件翻译取消后，各家的转圈状态一并结束。
- 原文骨架和 Markdown 预览里固定的正则只编译一次。
- 删掉划词浮层里什么都不做的全局鼠标移动监听。

没改：

- 实时字幕句子数量不设上限、偏好设置里 API 密钥每个字都写钥匙串、历史窗口在主线程读文件、浮层观察整个配置对象。这些会慢，但要动的结构多，单独排期。
- 实时字幕停止时在主线程同步等识别队列、说话人音高计算和识别挤在同一个队列、识别通道 `prepare()` 在队列外写识别器、网络会话断网时一直等连接（`waitsForConnectivity`）。都是“可能卡一下”，没有实测到出错，等实时字幕单独整理时一起看。

## 为什么

用户要求“优化性能，提高鲁棒性”，选的是只修有把握的问题。两份只读审查列出了候选，逐条对照代码确认后才改；推测性的、要大改结构的留着。

## 考虑过

- 顺手把实时字幕和偏好设置的结构一起理顺。牵涉面大，和这次的快捷翻译、媒体字幕改动混在一起不好验证。
