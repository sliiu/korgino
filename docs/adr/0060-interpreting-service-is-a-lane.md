# 同传服务占一路，自带一条译文

同传服务是一种识别。声音一直送进去，原文、译文和译音边说边回来。第一批是千问 LiveTranslate 和 OpenAI gpt-realtime-translate，都走 WebSocket。它们和别的识别放在同一张目录里，密钥可以跟同一家的翻译服务共用，连接地址只用自己的。

实时字幕里，同传服务占一路。这一路带一条「同传」绑定，译文就是服务给的，不再调翻译服务。一路只有一条同传绑定，因为一条连接只译成一种语言。改这条绑定的语言会重连，从下一句起生效。这一路照样可以再挂别的翻译服务，翻同传给的原文。服务说完的一句就是一段字幕，没说完的是草稿。同传那块沉浸字幕开着朗读时，放服务给的译音，不走朗读服务。

按住 Fn 时，选的识别是同传服务，就整条交给它。语音识别只要它的原文。语音翻译边说边出译文，松开后写进输入框。语音传译边说边放译音，读完再收起浮层。译文是服务给的，不再润色原文。

媒体字幕不列同传服务。它处理整份文件，没有边听边出的需要。

同传服务标出的说话人就是这一路的说话人。声纹装好之后不再把这一路重分一次，除非分说话人那一行打开「同传也按声纹再分」。默认关。会议记录里点「按声音重新分说话人」仍是自己选的，不受这个开关约束。

千问同传的译音音色在识别这一家的配置里选，不在朗读里。空着用服务的默认（Tina）。选了就在连接时发给它，下次开始生效。OpenAI 同传没有这张名单。沉浸字幕开着朗读时放的仍是服务送回来的译音，所以用的就是这一把。

## 考虑过

- 同传作为一种翻译服务挂在任意一路上：译文要等别的识别先出字，链路没有变短。
- 同传单独做一个功能，不进路网：标记、导出和一场笔记都得再做一遍。
- 只用服务的译文，不播译音：朗读仍要等整句合成，语音传译的延迟主要在这里。
